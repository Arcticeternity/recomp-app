# 增肌减脂饮食规划 APP · 开发规划

> 项目代号：`recomp_app`（body recomposition，增肌减脂的健身术语）
> 技术栈：Flutter（跨平台原生 App）
> 状态：已定稿 · 2026-09-12

---

## 一、产品定位与设计原则

**一句话定位**：不是卡路里计算器，是「供能结构校准器」——把"每天吃多少"从模糊焦虑变成可执行的配比，再通过 10 天周期微调逼近目标。

**三条底层原则**（贯穿所有模块，来自生活化减脂逻辑）：

1. **结构优先于热量** — 核心是碳蛋脂比例，不是精确卡路里赤字。总热量由「体重 × 配比」自然推导，用户不用算热量。
2. **减脂 ≠ 减重** — 目标是优化供能结构、保肌肉减脂肪，不追短期体重数字。
3. **自主微调** — APP 只给方向和边界，不替用户做决定。操作必须轻，避免过度依赖。

## 二、宏量营养素计算规则（核心）

### 2.1 配比总表（g / 公斤体重 / 天）

**男生（按周训练时长细分）**

| 周训练时长 | 碳水 | 蛋白质 | 脂肪 |
|:---:|:---:|:---:|:---:|
| 2-3 小时 | 2.2 | 1.4 | 0.8 |
| 4-5 小时 | 2.5 | 1.6 | 0.9 |
| 6-7 小时 | 3.0 | 1.7 | 1.0 |
| 8-9 小时 | 3.5 | 1.8 | 1.0 |

**女生（不按训练时长细分，取区间中点作为默认起始值）**

| 项目 | 配比区间 | 默认值 |
|:---:|:---:|:---:|
| 碳水 | 2.0 – 2.5 | 2.25 |
| 蛋白质 | 1.4 – 1.8（同男生区间） | 1.6 |
| 脂肪 | 0.9 – 1.1 | 1.0 |

> 女生默认取区间中点，理由是：调整逻辑是「减脂过快→提碳水、过慢→降碳水」，起点放在中点才能保留上下双向调整空间。区间本身作为「可调范围」暴露给用户，配比说明会提示。

### 2.2 计算公式

```
每日某宏量(g) = 当前体重(kg) × 对应配比(g/kg)
每日总热量(kcal) = 碳水×4 + 蛋白质×4 + 脂肪×9
```

> 热量换算常数：碳水 4 kcal/g、蛋白质 4 kcal/g、脂肪 9 kcal/g（营养学常识）。

**落地示例（85kg 男生，2-3 小时/周）**：

| 宏量 | 推导 | 结果 | 热量 |
|:---:|:---:|:---:|:---:|
| 碳水 | 2.2 × 85 | 187g | 748 kcal |
| 蛋白质 | 1.4 × 85 | 119g | 476 kcal |
| 脂肪 | 0.8 × 85 | 68g | 612 kcal |
| **合计** | — | — | **≈1836 kcal** |

### 2.3 「配比说明」自动生成

由两部分拼装：

**(1) 数值推导** — 模板化输出：
> "按你当前 85kg、每周训练 2-3 小时：碳水 2.2×85=187g、蛋白质 1.4×85=119g、脂肪 0.8×85=68g。碳水供能 748 kcal，占比约 41%。"

**(2) 性别差异化设计原因**（设计逻辑，非绝对科学论断）：
- **蛋白质不区分性别**：增肌所需蛋白与训练刺激相关，与性别弱相关，女生直接用男生同一区间（1.4-1.8）。
- **女生脂肪下限更高（0.9-1.1 vs 男 0.8-1.0）**：脂肪摄入过低会干扰雌激素与月经周期，女性需保留更高的脂肪安全下限。
- **女生碳水不按训练时长细分**：女性睾酮水平远低于男性，训练量对碳水需求的边际弹性更小，再细分收益低；同时避免女性用户陷入精细化计算焦虑，符合「轻量引导」原则。

## 三、核心逻辑流程（端到端）

```
用户档案(性别/体重/训练时长)
        │
        ▼
[计算引擎] 宏量配比 → 每日目标额度(P/C/F)
        │
        ▼
[录入] 每餐食物 → 换算宏量 → 累计已摄入
        │
        ▼
[统计] 已摄入 vs 目标额度 → 剩余可摄入
        │  ▲
        │  └── 修改/删除任一录入 → 自动重算（增量更新）
        │
        ▼
[周期校准] 每10天 → 记录体重趋势+体态图
        │
        ├─ 减脂过快(疑似肌肉/水分流失) → 碳水 +10~15g/天
        ├─ 减脂过慢 → 碳水 -10~15g/天
        └─ 正常 → 维持
        │
        ▼
[辅助参考] 训练欲望 / 睡眠质量 → 纳入调整说明
```

## 四、功能交互框架

### 页面结构（4 个 Tab + 1 个设置页）

| 页面 | 核心内容 | 关键交互 |
|:---|:---|:---|
| **① 今日** | 三宏量环形进度条、剩余额度、已吃食物列表 | 点「+」录入；点食物可改/删 |
| **② 计算** | 配比结果 + 配比说明 | 修改体重/训练时长即时重算 |
| **③ 周期** | 体重趋势图、体态对比、校准建议 | 每10天打卡，触发调整 |
| **④ 指南** | 三餐模板、钠盐管理、防反弹说明 | 静态知识页，可收藏 |

### 核心交互规范（轻量引导）

- **3 次点击内完成一次食物录入**：选餐别 → 搜/选食物 → 定重量 → 完成。
- **默认值友好**：常用食物带默认份量（如「1 碗米饭 = 150g」）。
- **不弹广告、不强行提醒**：只在 10 天周期节点 + 用户主动打开时提示。

## 五、食物录入与统计模块

### 5.1 两种录入方式

1. **手动录入** — 输入食物名 + 重量，用户自填 P/C/F 三项（或选填）。**支持自定义小众食物**，录入后存入个人食物库可复用。
2. **食物库匹配** — 内置常见食物数据库（预置 JSON 种子库），按名称模糊搜索，自动带出每 100g 的碳蛋脂，按录入重量折算。

### 5.2 统计维度与实时重算

- 维度：**每餐**（早/午/晚/加餐）和**单日** 两个层级的 P/C/F 汇总。
- 对比：`剩余额度 = 目标额度 − 已摄入`，剩余为负时高亮提示。
- 重算策略：数据模型维护「当日已摄入 P/C/F 累计值」，增/删/改单条录入时做**增量更新**，保证流畅。

## 六、动态调整模块（10 天校准周期）

### 6.1 触发机制

- 固定饮食 **7-10 天**后（APP 在第 10 天节点提醒），引导录入：**体重 + 体态对比图**（前后照片）。
- 辅助采集（可选）：本周训练欲望（高/中/低）、睡眠质量（好/中/差）。

### 6.2 调整规则

| 反馈信号 | 判断 | 动作 |
|:---|:---|:---|
| 减脂过快（周降幅明显超标 / 训练状态差 / 睡眠变差） | 疑似肌肉、水分流失 | **小幅提碳水** +10~15g/天 |
| 减脂过慢（体重/体态 10 天基本无变化） | 供能结构偏保守 | **小幅降碳水** -10~15g/天 |
| 正常（体重缓降 + 体态收紧 + 训练状态稳） | 结构合理 | 维持 |

### 6.3 调整说明输出

每次调整生成结合**性别 + 运动数据**的说明。示例：
> "过去 10 天你体重下降过快（-1.8kg），且训练欲望偏低，可能伴随肌肉/水分流失。结合你每周 6-7 小时的训练量，建议把碳水从 3.0 上调到约 3.1 g/kg（约 +10g/天），蛋白和脂肪不变。下个周期观察体重降幅是否回落到每周 0.5-1kg 的合理区间。"

### 7.2 钠盐管理

- 每日盐摄入目标：**6-8 克（盐，非钠）**。
- 换算提示：**1g 钠 = 2.5g 盐**（NaCl 分子量 58.5，钠 23，故 盐 = 钠 × 2.5）。
- 常见高隐形盐食物：15ml 生抽 ≈ 2g 盐、泡面酱包、香肠/火腿、咸菜/榨菜、豆瓣酱、蚝油、鸡精、火锅底料、薯片、话梅。

### 7.3 防反弹说明（固定文案）

> "减脂 ≠ 减重。你追求的是**调整供能结构**——让身体用碳水供能训练、用蛋白质保住肌肉、用脂肪守住激素，从而减掉脂肪而非水分和肌肉。短期内体重不降或小幅波动是正常的，别用体重焦虑惩罚自己，也别因为焦虑过度节食导致代谢受损。看趋势、看体态、看训练状态，而不是盯着每天那 0.1kg。"

## 十一、自定义碳蛋脂配比（v16.1 新增）

**需求**：允许用户在设置里自己定碳蛋脂比例，不再只能用配比表的推荐值。

**口径决策**：输入单位沿用 **g/kg 体重**（与应用既有逻辑、10 天校准一致），
不做供能百分比输入 —— 百分比是另一套反推模型，会让校准引擎失去统一基准。
预览区仍会算出供能占比，作为参考展示。

- **范围**：全局一套配比（不分训练日/休息日）。
- **持久化**：`settings` 表存 JSON（key = `macro_ratio`），**无需数据库迁移**。
  只存用户设定的配比本身；推荐值随「性别 + 训练时长」实时重算，不入库
  （否则用户改了训练时长会用到过期快照）。
- **文件结构**：
  - `lib/core/macro/macro_ratio_settings.dart` — 配比状态（生效值 + 推荐值 + 是否自定义）
  - `lib/core/macro/macro_ratio.dart` — 加 JSON 序列化 + `MacroRatioBounds` 区间夹取
  - `lib/pages/macro_ratio_page.dart` — 编辑页（滑块 + 数字输入 + 实时克数/占比预览）
  - `AppState.macroRatioSettings` / `AppState.dailyTarget` — 生效配比的唯一汇聚点
- **重置行为**：UI 提供「恢复推荐」，一键清除自定义值回到档案推荐配比。

### 11.1 顺带修掉的两个既有缺陷

1. **校准建议从未写回配比**：`cycle_page` 算出 `newCarbsPerKg` 只渲染成文案，
   配置没有任何变化 —— 用户会以为已经生效。现补「应用建议」按钮，点击才写回
   （仍由用户决定，不自动改）。
2. **校准基于推荐值而非生效值**：自定义配比后若校准仍按推荐值算，
   建议就是从一个用户并没有执行的数字出发的。现改用 `macroRatioSettings.ratio`。

### 11.2 界面优化（同批）

- **修 Material 3 层级倒挂**：「深色练习簿」原 `surfaceContainer(#202125)` 比
  `surfaceContainerHigh(#18191C)` 还亮，弹层比卡片更暗。现按数字递增排布。
- **宏量语义色主题化**：新增 `MacroColors` / `StatusColors`（`lib/app_theme.dart`）。
  原来今日页进度条用固定的 `Colors.lightBlueAccent` 等亮色，而它们画在
  `scheme.primary` 上 —— 练习簿主题的 primary 是近白色 `#F2F1ED`，进度条直接看不见。
  现按背景亮度取色（亮底用 700 深调 / 暗底用 200 浅调），对比度 ≥ 4.5:1。
  日历页正负反馈色、收藏红心、计划图标色一并接入语义色。
- **设置页分区**：饮食目标 / 我的档案 / AI 识别 / 外观（原先卡片顺排无层级）。
- **消除重复实现**：新增 `lib/widgets/choice_card.dart`，引导页选项与主题列表
  原本各写了一遍同样的选中卡片结构，现统一。

## 十二、v16.2 修复与全局优化

### 12.1 配比编辑页无法输入数字（用户反馈）

**根因**：`_RatioSlider` 把「色点 + 标签 + 偏离标签 + Spacer + 输入框(固定 68 宽)」
塞在同一个 Row 里。而**偏离标签恰好在用户改动配比时才出现** —— 它一出现就把
输入框压到十几 dp：数字被裁（显示不全），点击区几乎消失（点不进去、输不了）。
一个布局缺陷同时造成了用户报的两个症状。

**修法**：
- 数字输入独占一行，宽度 84dp；单位 `g/kg` 移出输入框（`suffixText` 会再吃掉
  本就紧张的可编辑宽度）
- 新增 ±0.05 步进按钮，滑块降级为粗调（弱化 track/thumb）
- 提交逻辑改为「失焦或回车」；非法输入还原
- 「恢复推荐」按钮显隐改由 `_settings.isCustom`（数据层）决定，不再用
  「当前草稿是否偏离推荐」—— 否则把值调回推荐值时按钮会自己消失
- 输入框同步用 `onChanged` 追踪「是否正在敲字」，不再靠「有没有焦点」猜
  （只聚焦未编辑时，外部改值会同步不进来）

### 12.2 AI 提示词优化

`AiService.systemPrompt` 公开为常量以便单测校验，约束按**错误代价**排序：

- 数据须符合常识（碳水/蛋白 4、脂肪 9 kcal/g 换算后落在 30–900 kcal/100g）
- **不确定宁可返回 0，也不编造** —— 编造值会一路污染到 10 天校准的建议
- 中餐按常见做法取值；生熟区分；每 100g 可食部口径
- 复合菜品按整道菜估算，不拆成多个对象
- 给两条示例输出以稳定格式

同时修解析器 `parseAiNutrition` 的两个缺陷：
- 旧正则 `\{[^{}]*\}` 无法匹配嵌套对象 → 改为括号平衡扫描（正确跳过字符串内的花括号）
- 数值非法（负数 / 非数字 / null）不再直接透传 → 回退安全默认值

超时 15s → 20s（移动网络偏紧）。

### 12.3 全局界面优化

- **窄屏适配**：新增 `test/narrow_screen_layout_test.dart`，在 320dp / 360dp 下
  遍历全部页面断言「零布局溢出」。它抓出并修掉 4 处真实溢出：
  今日页 header 的「今日摄入 + 卡路里」、`_RemainingMacro`、
  `_AnimatedMacroBar` 标签行，以及周期页的「体重曲线 + 7天/30天/全部」。

## 十四、Web 版（v16.4）

### 14.1 为什么不是「直接 build web」就行

原代码在 4 个文件里依赖 `dart:io` 与 `sqflite`，两者在 Web 上都不存在：

| 障碍 | 处理 |
|---|---|
| `sqflite` 无 Web 实现 | 引入 `sqflite_common_ffi_web`（sqlite3 WASM），factory 按平台切换 |
| `dart:io` 的 `Platform`/`File`/`Directory` | 条件导入（`if (dart.library.js_interop)`）隔离到 `*_io.dart` / `*_web.dart` |
| `getDatabasesPath()` 在浏览器无意义 | 抽象成 `dbDirectory()`；Web 返回空串 → 走内存库（由 ffi_web 持久化到 OPFS/IndexedDB） |
| 两个静态库（食物 116KB / 健身 404KB）按**文件路径**打开 | Web 改为把 **SQL dump** 灌进内存库（见下） |

### 14.2 静态库为什么用 SQL dump

`sanitize`：浏览器没有可写文件系统，`File(path).writeAsBytes` 不可用。

试过二进制反序列化，但 `sqlite3 3.6` 没暴露 `deserialize`，而 ffi_web 的
VFS 目录名属实现细节、不该硬编码。最终选 SQL dump（走公开 API、跨平台稳定）：

- 生成：Python + `sqlite3` 模块，见 `tools/dump_static_db.py`
- **每条语句必须占一行**：数据里含 JSON（带分号），按分号切会切坏，按行切才安全
- 产物 `assets/{food_composition,fitness}.sql` 作为 asset 打包
- IO 平台**行为不变**（仍复制 `.db` 文件）—— 不拿已验证的移动端路径冒险

### 14.3 部署注意：必须带 COOP/COEP 头

`sqlite3.wasm` 依赖 `SharedArrayBuffer`，浏览器要求页面**跨域隔离**才允许：

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

**缺这两个头，Web 版会卡在数据库初始化**。随手 `python -m http.server` 是不行的 ——
项目提供了带头的预览服务器：

```bash
flutter build web --release
python serve_web.py          # 默认 8080，带 COOP/COEP
```

已实测：`crossOriginIsolated=true`、`SharedArrayBuffer` 可分配、
`food_composition.sql`(193KB) 与 `fitness.sql`(370KB) 均 200 加载。

### 14.4 其他改动

- 补 Web 平台脚手架（`flutter create --platforms=web`）
- `web/index.html` / `manifest.json`：标题、描述、主题色（`#1B5E20` 森绿）
- Web 图标复用选定方案 B（192/512 + maskable 安全区版本 + favicon）

**已知限制**：静态库每次启动都要重灌（约 1900 条语句），比原生慢；
Web 只是附加平台，移动端未做任何行为变更。
